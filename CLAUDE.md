# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

whodunit: blind trials for coding agents in the pi harness. An extension deals a hidden model per role, and the user ends each run with a score before the role and model are revealed. `README.md` is the spec (session flow, house rules, scoring) and `app/README.md` covers the app (parallel chats, keys, score card, sidebar states); read them before changing behavior.

Four pieces live here; data lives under `~/.pi/agent/whodunit/`:

- `app/`: Rust desktop frontend (macOS, built on the `rune` UI crate pinned by git rev in `Cargo.toml`). It drives pi over `pi --mode rpc --model whodunit/auto`.
- `scoreboard/scoreboard.mjs`: standalone Node scoreboard (`node scoreboard/scoreboard.mjs --since 2026-11-09 [--until …]`).
- `extension/index.ts`: the pi extension that does classification, session titles, decks, fan-out and `/done`. Its pure rules (score folding, the deck draw) live in `extension/rules.ts`. pi loads it through a symlink, `~/.pi/agent/extensions/whodunit` → `extension/`, so edits here are live on the next pi start. `extension/roles.example.json` is the sample config.
- `laws/`: the same rules in Bend2 (`rules.bend`), their claims (`LAWS.bend`) and proofs (`PROOF.bend`). `node laws/check.mjs` runs the proofs and compares `extension/rules.ts` with the compiled spec; run it after touching either. Needs `bend` (`~/.bend/bin/bend`).
- Data, outside the repo: `~/.pi/agent/whodunit/` (`roles.json`, `decks.json`, `runs.jsonl`, `app.json`).

## Commands (run from `app/`)

Toolchain is pinned to Rust 1.99.1 (edition 2024) via `rust-toolchain.toml`.

rune comes from the fork `vaporwavie/rune` (branch `whodunit`, pinned by rev), which adds `TextArea::plain`, `Button::show_shortcut`, `MarkdownStyle::prose_width`, `SplitView::sidebar_title` and the OpenCode theme's contrast fixes on top of upstream. Switch back to `anomalyco/rune` once those land there. To try rune changes locally, add a `[patch."https://github.com/vaporwavie/rune"]` pointing at a checkout, and don't commit it.

```sh
cargo build --release                      # build
cargo clippy && cargo fmt                  # lint / format
scripts/bundle.sh                          # release build, installs ~/Applications/Whodunit.app (macOS) or ~/.local/bin/whodunit + desktop entry (Linux)
cargo run --release -- -- --scoreboard     # print the scoreboard as Markdown and exit
cargo run --release -- -- --cwd ~/some/dir # run pi in that folder (app args go after a second `--`, read via rune::extra_args)

# Headless snapshot of a fixture scene, no pi process (scenes are registered in src/main.rs)
cargo run --release -- --snap out.png --scene fanout [--theme light|dark] [--scale 2]   # without --theme it follows the system

# Live E2E tests: real pi, real models, a few cents each. Always single-threaded.
cargo test --release --test live_pi -- --ignored --nocapture --test-threads 1
cargo test --release --test live_pi a_fanout_shows_every_answer -- --ignored --nocapture --test-threads 1
```

`cargo test` includes unit tests in `src/core/tests.rs`, offline session-isolation tests in `tests/parallel_tasks.rs`, and real background-service process tests in `tests/background_service.rs`, using a deterministic RPC peer and a temporary HOME. The service tests cover UI crashes, disconnected completion, pre-file classification, partial output, queues, dialogs and concurrent launchers; they stop their own service on teardown. `node --test extension/decks.test.mjs` checks concurrent deck draws. `tests/live_pi.rs` talks to real pi and models; each live test removes its own lines from `runs.jsonl`, deletes its session files, and restores `decks.json`, so the week's real data stays clean. Keep that cleanup in any new live test.

## Architecture

- **One shared `Core`** (`src/core.rs`, `Arc<Mutex<Core>>`) holds global config and the session list, the selected `Task`, and background tasks. Each UI task owns a service connection, folder, transcript, dialogs, queue, stats and toasts. `Core` dereferences to the selected task for view reads. The app's one window (`ui/window.rs`, state `Window`) reads it, and a menu bar icon (`menu_bar.rs`) reopens the window. `window.rs` keeps the state, keys, `poll`, `catch_up` and `view`; each part of the window is a child module in `ui/window/` (`sidebar`, `chat`, `composer`, `board` for the scoreboard page, `viewer`, `folder_picker`, and `tests`), so children use the parent's private fields directly. Shared view pieces are in `ui/parts.rs`. Views only read `Core` and call its command methods (`submit`, `end_run`, `abort`, `request_leave`, `answer_dialog`…).
- **Background service** (`src/service.rs`, `src/core/service.rs`): the same executable runs with `--background-service` before rune initializes. One service per HOME owns the pi children and temporary workspaces; the UI connects over a private Unix socket. An advisory lock protects startup and stale-socket cleanup. Each hosted chat has its own `Core` using the same reducer as the UI. Attach takes a serialized `Task` snapshot and subscribes under one lock, then streams outbound commands and inbound RPC records through a bounded queue. Outbound commands restore pre-agent prompts, pending responses and bash state. Slow clients disconnect rather than backpressuring pi. Service IDs also identify chats before a session file exists. Quit only detaches; `--service-stop` explicitly stops every child. This is not service-crash or reboot recovery.
- **pi RPC** (`src/pi.rs`): `Pi::Child` owns stdin/stdout in the service; `Pi::Remote` owns a UI socket. Both use LF-delimited JSON. `Core::request_leave` selects the chat immediately and queues attachment in `Core::unstarted`; `poll` starts it off the UI thread, and commands typed before attachment wait in the outbox. Reader callbacks hold weak references and route records by the UI task's generation, restoring the selected task before waking the window. Unknown generations are dropped. Dropping a UI `Core` closes sockets, not pi. Direct `Core::new` remains available for fixtures and isolated RPC tests; the app uses `Core::background`.
- **Extension ↔ app contract**: the extension writes custom session entries, `whodunit.deal`, `.done`, `.switch`, `.fanout-view` and `.fanout-pick` (constants in `src/transcript.rs`). Dialogs (role picker, end run, fan-out pick) arrive as `extension_ui_request` and are answered with `extension_ui_response`. The end-run select is recognized by its title (`END_TITLE`, "End this run") and its options read `5 · nailed it, great` down to `1 · failed`: a digit only highlights, ⏎ commits. Renaming any of these means changing the extension too. The `.fanout-pick` message's content is text, the prompt's images, then text: joined, its text blocks still read `User request:\n\n<prompt>\n\nYour answer:`, which `transcript.rs` parses for the prompt and reads the images from. The fan-out's progress widget reads `fan-out · A running · B done · C failed · 93s`; `ui/stage.rs` parses it into lanes, so its words are contract too.
- **The model and the role stay hidden** (the ground rule in `README.md`): `transcript.rs` never copies model or provider fields into the transcript. The role, size and agent show only via `Core::reveal()` after a `done` entry (sidebar role and agent icons and subtitles, fan-out notes, the extension footer and `/role`). Don't add UI or logging that leaks either before `/done`.
- **Ending seals the session**: after `done`, `Core::submit` refuses everything but slash commands and the composer gives way to an ended panel with **New task**; the extension's `input` hook refuses prompts too, for plain pi.
- **Parallel chats**: one task per chat, but any number of chats may work at once. `request_leave` (`Leave::{New, NewIn, Open}`) navigates without a scoring guard or abort. The sidebar groups sessions by `Core::session_state`: Working, Idle (including dialogs waiting for input), Ended. Scoring and aborting affect only the selected chat. `Window` keeps each task's `Draft` (composer, dialog field, attachments) by task ID and swaps it whole on a switch.
- **Session files** (`src/sessions.rs`): pi stores sessions under `~/.pi/agent/sessions/--<cwd with / \ : as ->--/` (`config::session_dir`). The sidebar lists every folder's dealt sessions and reads each one's folder from its header line. Opening one shows its transcript from the file in the same frame, then starts pi with `--session` in that folder; a live chat keeps its process. The handler that navigates calls `catch_up`, so that frame is already the new chat, settled (`Tx::settle`), with nothing animating over from the last one. pi writes a file only after the first assistant message, so live chats (including classification and fan-outs before the first answer) are overlaid from memory.
- **Scoreboard sprites**: `assets/sprites/{roles,models,deciders}.json`, keyed by role name, stable artwork key and deal source (`jev`, `picker`, `forced`, `fallback`), each with a `fallback`. `assets/sprites/model-aliases.json` explicitly maps provider/model IDs to model artwork keys; it affects only icons, never scoreboard identity. `src/sprites.rs` upscales them nearest-neighbour once at startup to twice their point size, so they stay exact at 2×. The assets are compiled in, so changes need a rebuild.
- **Scoreboard exists twice**: `src/scoreboard.rs` (the app's page and `--scoreboard`) and `scoreboard/scoreboard.mjs`. Both join `runs.jsonl` with session-file metrics. Both also show who decided each role (Jev, picker, `/role`, fallback) from the deal's `source`. Ranking rules (mean score vs fan-out win share, `TOO_FEW = 3`, 10-minute idle cap) come from `README.md`; a change to one implementation needs the same change in the other.
- **Environment**: a Finder-launched app gets launchd's bare env, so `config::login_env()` runs the login shell once (`$SHELL -lic`) to find `pi` and the API keys. These are kept in memory only, never written to disk.
- **Images**: `transcript::Shot` holds a prompt image's bytes (sniffed as PNG, JPEG, GIF or WebP), decoded from pi's base64 once. The composer takes them from paste (`on_input_paste`, which rune_kit's `TextArea` doesn't forward, hence `composer_field` in `ui/window/composer.rs`) and from drops on the chat; `Core::submit_with` sends them as the prompt's `images`. Tiles decode through the window's `ImageCache` (`HasCore::image`), which only draws PNG and JPEG; other formats show their name. A click on a tile opens it in the viewer (`Window::viewing`, a modal overlay, in `ui/window/viewer.rs`), sized from `Shot::dimensions`, read from the file header so it's right before the decode lands. rune's `open_url` takes only `http(s):` and `mailto:`, so `parts::link_path` catches transcript links to local files first (absolute, `~/`, `file://`, or relative to the chat's folder): an image opens in the viewer, anything else is revealed in Finder, never opened.
- **Context meter**: `Stats::context_percent` is pi's context count over the point where pi auto-compacts (`config::compaction_reserve` reads pi's settings like pi does), so 100% is the next compaction. Stats are re-asked on each response, `turn_end`, `!` command and compaction; after a compaction pi's count is null until the next response, so the compaction's `estimatedTokensAfter` stands in (`Stats::predicted`).
- **Stage** (`src/ui/stage.rs`): small dot art at the transcript's tail while the selected chat works, on the shore's dot grid and painted by the same compositor (`dither::Waves`, which dispatches on `stage::MARK`), A deck of cards riffles and deals one off while the prompt is classified and dealt (and behind the role picker). The rest is kept quiet, grey static, scanlines and one neon accent: a fan-out gets one slim lane per contender, laid where its answer card will land, whose data bus streams while it answers, locks in the accent when done, and breaks into static when it fails. Thinking blocks stay out of the transcript before the reveal; the purple tide is the only thinking indicator. After the reveal the text shows down a dotted rail (`stage::rail`). While the agent works or thinks (`Stage::tide`), the shore's shader (`dither::tide`, same `dither::MARK`, a flag in its payload) draws a horizontal swash just above the composer: a solid crest over thinning water, in ink (no blue), haze purple and higher while the live message thinks, red while `Core::troubled` (a provider error being retried or toasted, any error toast, pi gone). An error toast or retry also holds an idle chat's tide in until it clears. The shade travels in the payload's flag bits (`dither::Shade`) and `dither::Tide` eases it while the water is in; a draining tide keeps its colour. While it thinks, the tide is a neural net: `poll` hands `Tide::tick` the live thinking block (`window::live_thought`), and each burst of it fires (`dither::Pulse`: a fast spike, slower activity, and a seed hashed from the burst's bytes that picks which neurons fire). Fired neurons on the crest throw needle spikes; deeper rows light their wires. `Shade::heat` grows with the thought's length and time and blends the haze toward `HOT_*`. Only the length and the hash leave the transcript, never the text. The payload's four floats are packed: flags (with heat), level, the dock (`pack_dock`) and the pulse (`pack_pulse`). It keeps clear of the chat's edges and of the composer's column, whose rect comes from `on_layout` (`Window::dock_rect`, `tide_rect`). `dither::Tide` brings it in and out on `poll`'s clock: it rises from below the slot on a stiff spring with a small overshoot when work starts, and falls away when the turn ends, and snaps to the target when motion isn't live. The transcript's tail keeps an empty `stage-tide-gap` row so the last lines clear its crest. `Stage::of` picks the state from `Core`; `LaneClock` times each lane's settle. It follows the shore's motion rules (paused while unfocused, held still under Reduce Motion) and `poll` paces it at `dither::FRAME`. When a turn settles (`Task::turns`), `ui/develop.rs` runs one scanner pass down the answer it ended on: its slot reads the backdrop (window-sized, even inside a layer) and redraws the answer's own glyphs as ordered dither, cooling back to crisp text; the `developing` scene is its halfway frame.
- **Fixtures** (`src/fixtures.rs`) build fixed transcripts for the headless scenes (`empty`, `chat`, `end`, `reveal`, `fanout`, `dealing`, `working`, `tide` (halfway in), `thinking`, `thinking-deep` (a long thought, net busy), `trouble`, `fanning`, `attach`, `viewer`, `run`, `tasks`, `long`, `wide`, `busy`, `slash`, `slash-empty`, `shell`, `growing`, `board`, `picker`, `picker-cmd`). The screenshots in `docs/` (used by both READMEs) are the `run`, `end` and `fanout` scenes at `--scale 2`. Add a scene there and register it in `main.rs` when adding UI states.
